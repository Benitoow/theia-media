# Theia 3.3.3: one picture everywhere, and rooms in the settings

If you use Windows x64, download this one file:

**[Download Theia 3.3.3 for Windows x64](https://github.com/Benitoow/theia-media/releases/download/v3.3.3/theia-setup-windows-amd64.exe)**

It installs the server, the native player, the `theia` command and the pinned
video engine, verifies every downloaded byte against GitHub's SHA-256 digest,
puts the installation on your `PATH` and registers it with Windows. If this
machine must install without a network connection, use the
**[complete offline bundle](https://github.com/Benitoow/theia-media/releases/download/v3.3.3/theia-3.3.3-windows-amd64.zip)**
instead, unpack it and run `theia-setup.exe`.

Everything else under *Assets* is a component consumed by the installer or the
automatic updater.

## What changed

- **The home's picture is the library's picture.** One recipe on every tab now:
  the featured film's backdrop is softened and melted into the page - away to the
  left, where the copy is, and away at the bottom - instead of sitting on the page
  as a rectangle. The hero's own scrims are gone with it, because the copy no
  longer sits over the picture at all. If the seam looked wrong, it was: the two
  halves of the product were drawing the same artwork in two different ways.
- **The settings sheet is a rail and a panel.** Interface, Playback, Server and
  Update down the left, the chosen section on the right. The language, the two
  playback preferences, the connected server and the update state each live
  behind their own heading instead of one long scroll. The sheet is wider than it
  was - the update row and its Check button used to hang out of the panel - and
  the footer is a bordered **Cancel** beside a filled **Save**.
- **The server address can be copied.** Behind Server, beside the address itself,
  with the confirmation in whichever language the application is speaking. The
  row ellipsises a long address; the button copies the whole one.

- Go: `go vet ./...` clean and `go test ./...` green across every package.
- The native player: `cargo test` 11/11, `npm run check:i18n` (fr 140 / en 140),
  `npm run check:types` clean, and `npm run check:render` green - including the
  journey that walks all four settings sections, reads the copied server address
  back **from the clipboard** rather than trusting the sentence beside it, and
  measures each panel for sideways overflow.
- The real window: photographed on the home, the Films tab and the Series tab at

- The web application is untouched since 3.3.2 except for its version number;

Not driven here: **Flow Launcher's own window and the Windows search box**, which

## Post-publication verification

Published on 21 September 2026 by release workflow
[`35599498573`](https://github.com/Benitoow/theia-media/actions/runs/35599498573).
Every validation, rollback/endurance, platform build, player and publish job
completed successfully, and the release page shows exactly the ten intended
assets, each with a GitHub SHA-256 digest - `scripts/check-release-assets.ps1`
accepts those ten names unchanged. All ten were downloaded again from the public
release and every digest matched, sizes included: the installer
`sha256:487e8b1a6a30730d8cef4c806a97d9031908777d8a446cf5714bf95c69672621`, the
offline bundle
`sha256:abf5e82f7cc949e6c6973cd56c7855fddb42a9a9065e123cd1905e90de7e996d`. The
installer reports `theia-setup v3.3.3`, the published server and the `theia`
command both report `theia v3.3.3`, and the published server, started against a
throwaway data directory, answers `/api/health` and serves the real interface
from `/` with `TMDB metadata enabled` in its log.

**The server inside the offline bundle was not that build, and the fault is
older than this release.** Started the same way, the `theia-server.exe` inside
`theia-3.3.3-windows-amd64.zip` answers `/` with **503 and the placeholder
page** - "The server is running, the interface is not built" - and logs
`no TMDB API key configured, only cached metadata and artwork are available`. It
is 17 496 064 bytes against the published server's 18 626 560 because it is a
second build: the archive is assembled in the player job, which never downloaded
the `embedded-web` artifact into `web-dist` and never passed `TMDB_API_KEY` to
`build-release.ps1`. Measured on the 3.3.2 bundle as well - byte for byte the
same size, the same two symptoms - so every archive released since decision 121
introduced it has carried a server without the interface and without the
metadata key. The published `theia-server-<os>-<arch>` assets were never
affected: they are built in the build job, which does both. The bundled binaries
also report `3.3.3` where the published ones report `v3.3.3`, which nothing
depends on - the updater's version pattern takes the leading `v` as optional.

Fixed in `release.yml` before this record was written: the player job now
downloads the interface artifact, the assembly step is handed the metadata key,
the archive's server is **run** and required to answer `/` with the interface
and to report `TMDB metadata enabled` before anything is published, and the
published Windows server is scanned for the built application's `/_app/` asset
path. Both checks were proved to discriminate before being trusted - against
today's bundle they fail, against the published server they pass.

**And the release was re-cut rather than left to the next update.** The first
publication was withdrawn, the tag was moved onto the fix, and the workflow
republished the release from it
([run `35621749285`](https://github.com/Benitoow/theia-media/actions/runs/35621749285)).
That run's first attempt failed inside the interface guard - one WebKit
assertion of the playback journey asked for the playhead to pass 11 seconds
within five and saw 8 on a shared runner, every other test passed, nothing was
published, and the retry passed it. The new archive is
`sha256:73146aaf7191d505f68c4def5a33f234427d0ad608d49077c960fbd8d3d2c6ad`
(62 362 286 bytes), holds its eight files, and its server answers `/` with the
interface and logs `TMDB metadata enabled` - the same two questions the new
guards ask before publishing.

The nine other assets were re-uploaded with it, and eight of them are not
byte-identical to the first uploads although no Go source moved between the two
tags: Go stamps a build ID, and the frontend is not byte-reproducible -
SvelteKit writes the build time into the bundle (`{"version":"1789993574098"}`
then `{"version":"1790005895723"}`), which changes the emitted chunks and their
content-hashed names. The installer and the launcher, which embed no frontend,
came back identical to the byte. Every asset matches its own advertised digest,
which is what the installer and the updater verify.
