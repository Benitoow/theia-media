# Theia 3.3: the native generation

V3.3 changes what Theia *is* on the machine in front of you. Until now, films
were watched in a browser, and the browser has a ceiling that no amount of work
on our side removes: it cannot hand a TrueHD or DTS-HD MA stream to an
amplifier, it carries only the HDR10 base layer of a Dolby Vision profile 7 file,
and it does not read Matroska natively. Those are properties of the platform.

So the product is now three programs instead of one:

| | |
|---|---|
| **`theia-server`** | The server you already know: indexes folders, holds the library, serves the interface and the files. Still one Go binary, still no dependencies beyond the FFmpeg it downloads itself. |
| **`theia-player`** | A native player: a small window, the film drawn by libmpv, and the same interface floating on top of it. This is where films are meant to be watched now. |
| **`theia-setup`** | The installer. It asks what the machine is for, writes the configuration, and can put the server on autostart without asking for administrator rights. |

The browser interface has not been taken away. It remains the full
administration surface and a working fallback player for anything a browser can
decode; it simply is not where the best picture and sound live any more.

## What the player actually does

- **Your sound reaches the amplifier.** Passthrough is requested for
  AC-3, E-AC-3, DTS, DTS-HD and TrueHD. On a machine whose audio endpoint refuses
  the raw stream, the player notices the film has not started, withdraws the
  request, re-establishes PCM, and reloads **from where it was** rather than from
  the beginning - then says why, in the interface, as a sentence rather than an
  error code.
- **Matroska, Dolby Vision, HDR.** The file is read as it is, with `d3d11va`
  hardware decoding and the `gpu-next` renderer on a 10-bit swapchain.
- **It resumes where you stopped**, and it writes that position back to the same
  table the browser player writes to. Start a film in the browser, finish it in
  the player, or the other way round.
- **Subtitles beside the film work.** A `.srt` next to the video is found by the
  server and handed to the player, which a browser cannot do over HTTP. Embedded
  subtitles, including bitmap ones, are read from the file itself.
- **The library is the library.** The player browses the same catalogue, as a
  card grid, with the same artwork and the same progress marks.

## Setup, and what it will not do

**One file is the download.** `theia-setup-windows-amd64.exe` - about 13 MB - and
it fetches the rest: the server, the native player, and the media engine the
player uses. Every file is checked against the SHA-256 digest GitHub publishes for
it, and a download that does not match is deleted rather than kept. The programs
are copied into `%LOCALAPPDATA%\Programs\Theia`, and entries appear in the Start
Menu under **Theia** and on the Desktop, so the product can be launched by name -
from a launcher such as Flow Launcher as much as from the menu.

Nothing is downloaded if you would rather not: the release also publishes
`theia-3.3.0-windows-amd64.zip`, holding every file. Unpack it, run
`theia-setup.exe` from inside the folder, and it copies what is beside it with no
network at all.

`theia-setup` asks five questions - the role, where the data lives, the port, the
name on the network, the folders to scan - and shows the whole plan before writing
anything. It does **not** guess what the machine is for: a mini-PC in a cupboard
and a home-theatre PC share a hardware fingerprint, so you answer - all-in-one,
server only, or player only. It installs an autostart entry only if you ask, and
**it never requests administrator rights**. On Windows that means a per-user
Startup entry when the installer is not elevated, and a scheduled task when it is;
the tool tells you which one it used instead of substituting one for the other
quietly.

The command line does everything the form does, for a scripted or repeatable
install: `--role`, `--data-dir`, `--install-dir`, `--library`, `--port`,
`--service`, `--from`, `--json`. `theia-setup --check` reports what the machine is
configured as, and `theia-setup --update` updates the server through the same
digest-verified path the server uses on itself.

## Getting it, and upgrading from 3.2

**Download one file**: `theia-3.3.0-windows-amd64.zip`. Unpack it anywhere and
run `theia-setup`. Everything is in there - the installer, the server, the
player, the media engine the player uses, that engine's licence - and the
`START-HERE.txt` inside says which file to run. Nothing is downloaded during
installation, and nothing is written outside the folders you choose.

**Your existing installation updates itself normally.** The V3.3 release
publishes the server as `theia-server-<os>-<arch>` *and* keeps a byte-identical
copy under the old names (`theia-<os>-<arch>`) for this release only. An
installed v3.2 asks for the old name through the updater it already carries, so
it finds this release, installs it, and lands on a version that knows the new
names. **Those transitional copies are removed in the next release**, which is
what they are for.

If you want one piece rather than the archive, the individual assets are
published too: the server, the installer, and a player-only zip. The installer
finds a server and a player beside itself, under either their short names or
their published ones.

The player is a separate, replaceable program on purpose: point `THEIA_LIBMPV`
at your own build of libmpv and it will use that one instead of the one shipped
beside it.

Nothing is code-signed. Windows may show a reputation warning on first launch,
and macOS may require **Privacy & Security → Open Anyway**. Both are expected for
a project at this scale, and neither is a sign that something is wrong with the
download.

## What is verified, and what is not

This is the part most release notes leave out, and this project does not.

**Verified on Windows 11** (AMD Radeon 890M, mpv `v0.41.0-1049-g0b7ed670f`):
hardware decoding and rendering into the player's own window with zero dropped
frames; composition of the film and the interface; the audio fallback described
above; resume across a reload; track selection; a library of 250 films read in
full in two requests; and a real v3.2.0 installation updating into this release
through the transitional names - including the negative control, where removing
those names makes the same installation refuse to update with "no binary for
windows/amd64".

**Not verified anywhere:** bitstream passthrough reaching an actual amplifier -
the development machine has no AV receiver and one WASAPI endpoint, so the
mechanism is proven and the result is not; the composite pixels of the interface
drawn over moving video, which needs a person looking at it; mDNS browsing end to
end, because multicast is dead on that machine; and **macOS and Linux, which are
written but have never been run**. The player is built for Windows only in this
release for exactly that reason. Television and mobile applications remain out of
scope; they are a later generation, not a promise.

## The engine, and its licence

The player ships libmpv, built for libmpv by
[`zhongfly/mpv-winbuild`](https://github.com/zhongfly/mpv-winbuild), release
`2026-09-14-0b7ed670f7`, LGPL-2.1-or-later. The archive and the library are both
pinned by SHA-256 in `player/libmpv.json`, the build refuses anything whose digest
does not match, and `theia-player --diagnostics` prints the source, both digests
and the version string the loaded library reports. The LGPL text travels in the
bundle, and the library stays a separate file you may replace.
