# Theia 3.3.4: the native generation reaches Apple Silicon

On a Mac with Apple Silicon, download this one file:

**[Download Theia 3.3.4 for macOS Apple Silicon](https://github.com/Benitoow/theia-media/releases/download/v3.3.4/theia-setup-darwin-arm64)**

If you use Windows x64, this is still your one file:

**[Download Theia 3.3.4 for Windows x64](https://github.com/Benitoow/theia-media/releases/download/v3.3.4/theia-setup-windows-amd64.exe)**

Both install the server, the native player, the `theia` command and the pinned
video engine, verify every downloaded byte against GitHub's SHA-256 digest, and
put the installation on your `PATH` - a Windows `PATH` and an App Paths entry, a
`~/.local/bin` link on a Mac, whose one-line addition to `PATH` is printed rather
than written into your shell profile. If a machine must install without a network
connection, use the offline bundle for
**[macOS](https://github.com/Benitoow/theia-media/releases/download/v3.3.4/theia-3.3.4-darwin-arm64.zip)**
or
**[Windows](https://github.com/Benitoow/theia-media/releases/download/v3.3.4/theia-3.3.4-windows-amd64.zip)**
instead, unpack it and run `theia-setup` or `theia-setup.exe`.

Everything else under *Assets* is a component consumed by the installer or the
automatic updater. There are fourteen of them now, and the macOS player bundle
and its archive are two of the new ones.

## What changed

- **macOS is a platform, not a server binary.** Apple Silicon gets the whole
  product: the native player, the installer, the `theia` command and an offline
  bundle. The player there **draws the film itself** - mpv 0.41 removed `--wid`
  on macOS, and the engine pinned for it cannot present a frame on its own, so
  the picture goes through libmpv's render API into a GL surface the player owns,
  with the interface composited over it. That is the mechanism the browser
  fallback cannot offer and the reason decision 117 exists.
- **The macOS download runs as it arrives.** A zip used to lose the executable
  bit, and the instructions had to teach four `chmod`s before anything would
  start. The archive is written with `zip -r -y` now, which keeps the permission
  bits and keeps the engine's symlinks as symlinks - so the bundle no longer
  carries eleven of its libraries twice, twenty-five megabytes of duplication
  that a flattened set made completely invisible.
- **The engine pin is named correctly on a Mac.** `--diagnostics` printed a page
  of nulls for the pin, because the player asked the manifest for `macos/arm64`
  where it is keyed `darwin/arm64`, and read `library` where the macOS entry
  said `engine_library`. The pin was there and correct the whole time.
- **The web player's control bar survives a phone width.** Below 44rem it drops
  the ten-second pair, the same control the native bar drops at the same width,
  and the clock keeps both numbers. Measured with a three-hour film's clock at
  seven widths, at rest and with the volume slider expanded.
- **The interface stops stamping its build time into the release.** Two builds of
  the same source now produce the same bytes, so a re-cut release is comparable
  with the one it replaces.
- **The launcher opens the interface when there is no player**, and the player is
  updated by the installer rather than by itself.

## Verification boundary

Everything below was run for this release, and the macOS half of it was run on a
GitHub-hosted `macos-14` runner - real Apple Silicon, standing in for the Mac
this project does not have.

- The release pipeline, dispatched without publishing: all six servers, both
  players, both archives, and the guard that checks the exact fourteen-name
  public surface. Its first runs found four real defects, all fixed here.
- On Apple Silicon: the pinned engine verified by digest, `mpv_render_context_create`
  succeeding with `MPV_RENDER_API_TYPE_OPENGL`, **the film on screen** and **the
  interface's own control bar over the GL surface**, both photographed during the
  run; the bundle compiling, signing and playing a fixture (`ao=coreaudio`, audio
  mode honestly `pcm`); the darwin server answering `/api/health` on a throwaway
  data directory; the installer installing into a throwaway home without a
  password, writing both links, writing the launchd agent when `--service` asked
  for it, and the uninstall removing it while keeping the data. The verifier
  reports 21 of its 21 checks passing.
- The archive is unzipped the way a person unzips it, and its four programs must
  be executable, its engine symlink present, and its `START-HERE.txt` free of any
  step it no longer needs.
- Go: `go vet ./...` clean and `go test ./...` green. Rust: `cargo test` 13/13.
  The web suite, the playback guard across four browsers, and the interface guard
  all green.

**What is not verified, and is not claimed.** Four things need a Mac rather than a
runner: whether the interface reads well over a moving film, whether sound
reaches an amplifier, Gatekeeper's first refusal of an unsigned download, and
hardware decoding - the virtualised runner accepted `hwdec=videotoolbox` and then
refused it (`Failed setup for format videotoolbox_vld`), so the film fell back to
software decoding and played. The macOS build is ad-hoc signed: there is no Apple
Developer certificate behind it, so the first launch is refused once and the
`START-HERE.txt` says exactly how to allow it.

## Post-publication verification

Published on 23 September 2026 by release workflow
[`35821865718`](https://github.com/Benitoow/theia-media/actions/runs/35821865718),
from the tag these notes were cut at. Every job completed successfully - the six
servers, both players, both archives, the interface guard, the macOS one-file
download, and the guard on the exact fourteen-name public surface - with
`publish` last.

**The first attempt failed, and it published nothing.** The tag was pushed once
before this one, and that run
([`35821286234`](https://github.com/Benitoow/theia-media/actions/runs/35821286234))
stopped at `package-macos`: the assembly step passed the tag straight through
where `build-release.ps1` takes the bare version, so the archive was written as
`theia-v3.3.4-darwin-arm64.zip`, and the step just below it unzipped
`theia-3.3.4-darwin-arm64.zip`, found nothing, and reported `the archive is
missing Theia.app/Contents/MacOS/theia-player`. A dispatched run cannot show
this - its version is `0.0.0`, which has no `v` to drop - so only a real tag
exposed it. Fixed the same morning: the assembly step strips the `v`, and the
bundle's `Info.plist` now carries `3.3.4` where `theia-player -version` prints
`v3.3.4`, because `CFBundleShortVersionString` is documented as a dotted number.
The tag was moved onto the fix and the workflow published from it. `publish` sits
downstream of both checks, which is why that cost a run rather than an upload.

All fourteen assets were downloaded again from the public release, and every size
and every SHA-256 matched the digest GitHub publishes: the Windows installer
`sha256:2b681b60…`, the Windows offline archive `sha256:7b346902…` (62 409 208
bytes, holding its eight files), the Windows launcher `sha256:f588c5e6…`, the two
macOS downloads a person actually wants - `theia-setup-darwin-arm64`
`sha256:4d3041e4…` and `theia-3.3.4-darwin-arm64.zip` `sha256:d1367f43…`
(33 652 879 bytes) - and the ten component assets an updater selects by name.
`scripts/check-release-assets.ps1` accepts those fourteen public names unchanged,
reading `release staging is exact: 14 assets for Theia 3.3.4`.

The three Windows programs say what they are: `theia-setup v3.3.4`, and `theia
v3.3.4` for the server and the launcher. Started against a throwaway data
directory, the published server answered `/api/health` with
`{"status":"ok","version":"v3.3.4","uptime_seconds":0,"language":"en"}`, served
the real interface from `/`, and logged `TMDB metadata enabled`.

**The server inside the offline bundle is the product this time.** Fault 14 was
that it was not: the archive's `theia-server.exe` answered `/` with the 503
placeholder page and carried no metadata key. Unzipped the way a person unzips
it, that server now answers `/api/health` with
`{"status":"ok","version":"3.3.4","uptime_seconds":0,"language":"en"}`, serves
`/_app/` from `/`, and logs `TMDB metadata enabled` - the same two questions the
new guards ask before publishing, asked again of the published archive. It
reports `3.3.4` where the published server reports `v3.3.4`, the same cosmetic
difference the 3.3.3 archive has, which nothing depends on.

**The four macOS assets cannot be run on this machine**, and this record does not
claim otherwise: their sizes and digests above are the evidence available here,
