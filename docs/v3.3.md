# Theia V3.3 - the native generation

V3.3 separates storage and routing from high-fidelity playback. The maintainer
instructed the pivot on 14 September 2026; its reasoning, and exactly which
founding clauses it supersedes, are recorded in decision 117 and
[`spec-fondatrice.md`](spec-fondatrice.md) §14.

## Current release line

`v3.3.0` published the native generation. `v3.3.1` is its first maintenance
release: it removes the one-release V3.2 asset aliases, makes Windows x64 the only
published installer because it is the only complete platform verified on real
hardware, and labels the installer and offline bundle as the human downloads.
The six server binaries and the Windows player bundle remain separate technical
assets because installed updaters and the installer select those exact names.
Decision 138 records the measured asset count and the release contract.

`v3.3.2` is the second, and it answers the question that installing 3.3.1 left
open - how does one launch it. It publishes the `theia` command (decision 139),
puts the installation on the user's PATH and in App Paths, points the product's
own entry at the launcher rather than at the player, and takes both back out on
`--uninstall`. It also fixes the empty-library fault 13, which the first
installation with no films in it found within a minute.

`v3.3.3` is the third: the settings sheet becomes a rail and a panel with a copy
button for the server address, and the home's featured picture uses the library's
own recipe - one treatment of a backdrop across every tab. The notes are
`docs/releases/v3.3.3.md`.

`v3.3.4` is the fourth, and it makes macOS a platform rather than a server target.
Apple Silicon gets the whole product: the native player, the installer, the
`theia` command and an offline bundle, all of it run on a GitHub-hosted
`macos-14` runner because this project has no Mac (decision 144). The player there
**draws the film itself** - libmpv's render API into a GL surface it owns, with
the interface composited above it - because mpv 0.41 removed `--wid` and the
pinned engine presents no window of its own on macOS. The archive is written with
`zip -r -y` now, so it arrives runnable and keeps the engine's symlinks as
symlinks, and the public surface grows from ten names to fourteen. The notes are
`docs/releases/v3.3.4.md`.

## Scope

Three executable artifacts, one visual identity - and, since decision 139, the
command that starts them:

| Artifact | Language | Responsibility |
|---|---|---|
| `theia-server` | Go, no CGO | Folder indexing, SQLite, TMDB with a local cache, userspace WireGuard listener, mDNS announcement. Still serves the Svelte interface for administration and fallback playback. Published assets use `theia-server-<os>-<arch>`; the old `theia-<os>-<arch>` bridge existed in V3.3.0 only. |
| `theia-player` | Rust, Tauri 2, React, TypeScript, Vite, Tailwind | Native video and audio output. A shadcn/ui desktop shell with Lucide controls and Motion transitions sits over the native video surface; audio passthrough, track selection, resume and series playback remain Rust/libmpv responsibilities. |
| `theia-setup` | Go, Charm | Declares the machine's role, installs the service, verifies and applies updates: the server's through the server's own updater, the player's bundle through `--check-player` and `--update-player` (decision 143). |
| `theia` | Go | The command somebody types: starts the server if it is not answering, waits for it, then opens the player. `theia server` and `theia player` start one half. Windows-only, like the player, and published as `theia-launcher-<os>-<arch>.exe`. |

## Success criterion

The founding spec §10 asked for "a browser on the television, a film in fewer
than three clicks". V3.3 replaces that, because the browser is no longer where
films are meant to be watched:

> A film starts from `theia-player` on a machine that was set up once, at full
> quality, with its own audio track handed untouched to whatever the HDMI cable
> reaches - and the person watching never had to configure a codec, choose a
> transcode, or open a settings page.

The web interface keeps its own, lower bar: it must remain a complete
administration surface and a working fallback player for anything the browser
can decode.

## Non-goals

- **The web player is frozen.** `Player.svelte`, the MediaSource transport and
  the V3.2 playback engine stay as they are, serviced by `theia-server`. They
  receive regression and security fixes; no new capability.
- **No television or mobile application.** Android TV, Apple TV and iOS/iPadOS
  are deferred to a later generation. They add two toolchains and two store
  pipelines, and the project has one maintainer.
- **No second visual identity.** The native shell is implemented in React rather
  than pretending the server's Svelte page is a desktop application. It imports
  the same tokens, fonts and behavioural rules, so the implementation differs
  while Theia still looks and behaves like one product.

## Validation boundary

Windows is the only platform this generation can be verified on, and the machine
available for it has **no AV receiver and no HDMI passthrough path**: it
enumerates one WASAPI output, the Realtek speakers. Every claim below is
therefore either observed on this machine or explicitly marked unverified. In
particular, bitstream passthrough to an amplifier can be *configured and
accepted* here, but not *proven* here.

### Spike A3 measurements - the audio endpoint (Windows 11, Realtek speakers, no AVR)

The request path works and the endpoint refuses it, which is the useful answer:

- With `audio-spdif=ac3,eac3,dts,dts-hd,truehd`, mpv selects libavformat's
  passthrough decoder (`Selected decoder: spdif_ac3 - libavformat/spdifenc audio
  pass-through decoder`) and asks WASAPI for `stereo spdif-ac3`. The endpoint
  answers `-> unsupported` and **the audio driver fails to initialize**.
- The control run on the same endpoint, bitstream disabled, succeeds:
  `Accepted as 5.1(side) s32 @ 48000hz -> 5.1(side) s32 (32/24 bits) @ 48000hz
  (exclusive)`, `AO: [wasapi] 48000Hz 5.1(side) 6ch s32`. So the endpoint is
  healthy and the failure is specific to the bitstream format.
- **Consequence for the player, decided here.** Because the audio output was
  pinned to `wasapi` for passthrough, a refusal produced *no audio at all* -
  `current-ao` was absent rather than falling back. The player must therefore not
  present passthrough as a switch that either works or silently dies: it tries
  bitstream, falls back to PCM on refusal, and **says which one is in use**, with
  the reason when it is PCM. This is decision 117's "declares nothing it cannot
  observe" applied to the one place where the difference is audible.
- What this does **not** prove: that a TrueHD/Atmos or DTS-HD MA stream reaches
  an amplifier untouched. There is no receiver and no HDMI audio path on this
  machine, and the project will not claim that until someone watches a film that
  way.

### Spike A2b measurements - the OSD over the picture (Windows 11, Tauri 2.11.5)

A real Tauri 2 window (`transparent: true`, undecorated) hosting libmpv through
`wid`, with an OSD page above it: a top bar, a bottom control bar, and a
full-bleed viewport carrying `pointer-events: none` so a click on the picture
falls through to the player.

The child windows of the Tauri HWND, topmost first. That order is the whole
question, and it is the order the operating system composites:

| # | class | role |
|---|---|---|
| 1 | `TAURI_DRAG_RESIZE_BORDERS` | Tauri's resize frame |
| 2 | `WRY_WEBVIEW` | the WebView host |
| 3 | `Chrome_WidgetWin_0` | WebView2 |
| 4 | `Chrome_WidgetWin_1` | WebView2, titled by the configuration |
| 5 | `Chrome_RenderWidgetHostHWND` | the renderer |
| 6 | `Intermediate D3D Window` | WebView2's compositor |

- mpv honours `wid`: it creates its own child window, class `mpv`, and takes the

  rectangle in the same window.
- **No z-order forcing was needed.** mpv's surface lands beneath the WebView

- Playback inside that window, read from mpv at 7.6 s:
  `{"ready":true,"pause":no,"pos":"5.625000","dur":"6.000000","ao":"wasapi","vo":"gpu-next"}`.

**Verdict: `wid`, pending one look.** It also leaves HDR metadata, the flip-model
swapchain and the 10-bit format to mpv - spike A2a watched it choose

would hand Theia a D3D11 device, a swapchain and their formats to get wrong. The

**Not verified, and it is the only thing that matters next:** whether a film is

### Player skeleton - first light (Windows 11, mpv v0.41.0-1049-g0b7ed670f)

`player/` now holds the real thing rather than a spike: a Cargo workspace, the
`theia-player` crate, and a React/TypeScript desktop shell built by Vite. It
imports the web application's `tokens.css` and fonts directly, uses Tailwind for
layout, a shadcn/ui button primitive, Lucide for controls and Motion for state
transitions. No second palette and no imitation browser tab.

Verified on this machine, by running it:

- the engine loads through the FFI layer and reports
  `mpv v0.41.0-1049-g0b7ed670f`;
- an HEVC Main 10 Matroska file decodes with `hwdec-current = d3d11va`, renders
  through `current-vo = gpu-next`, and reaches the end of the file;
- TypeScript checking, locale parity and the Chromium render journey pass. The
  scrub bar has real keyboard handling, and the background click is filtered so
  a button press cannot toggle playback twice.
- the desktop shell owns ordinary window furniture: drag region, minimize,
  maximize/restore and close. Playback close is no longer confused with process
  exit.
- the library shell mirrors the web information architecture in one long
  Dynamic-Island-style bar: `THEIA`, Accueil, Films, Séries, Rechercher, Réglages
  and the active profile, and it opens on the home screen the web already had -
  a hero for the film that was left and the server's short rows (decision 130).
  Profile changes call the native client and reload the
  catalogue; profile names and pictures can be edited through the same server
  API as the web interface; the settings update badge and check/install actions reflect the
  server updater state instead of a local mock.

**The finding that changed the design.** On a machine whose endpoint refuses the
raw stream, mpv does not merely lose its sound: it never establishes an audio
output, so it never advances the film. `time-pos` sat at `0.000000` with the file
loaded and unpaused. A player that waited for the clock before concluding
anything was wrong would have waited forever - which is precisely what the first
version of the watchdog did, and the run showed it.

The trigger is therefore the absence of an audio output after a grace period,
not the playback position. Once the request is withdrawn and PCM re-established,
the same run reports `ao = wasapi`, `audioMode = pcm`,
`audioReason = endpoint-refused-bitstream`, and `pos` reaches `6.000617` of a
six-second file. Rust sends the code; the sentence lives in the OSD's catalogue.
That is decision 25 applied to a second interface, and it is the reason the
player has a catalogue of its own.

### The server client, and what this machine could not prove

`player/theia-player/src/server.rs` finds servers and talks to them. Its API
surface is small by design: the film itself is fetched by mpv rather than by the
player process, because mpv does range requests, buffering and seeking better
than anything written here would.

Two paths, deliberately unequal:

- browsing for `_theia._tcp.local` is the pleasant one, and the server now
  announces exactly that. It used to announce `_http._tcp`, which describes "a
  web server" and tells a client nothing about the product it found.
- an address typed by hand is the contract. That asymmetry is not new - it is
  the one the server already documents for mDNS versus the QR code - and this
  machine is the argument for keeping it: a query for *any* mDNS service here
  returns nothing at all, and the responder refuses an IPv6 multicast bind. mDNS
  is therefore written, running and **unverified**, and the test skips rather
  than lying about it. The Go side gained a test that browses for its own
  announcement the way the player does, so the claim runs wherever multicast
  actually works.

Verified end to end against a real server on `127.0.0.1:8395` holding generated
films: connect, adopt the single profile, resolve a film to its primary file,
play it over HTTP, recover from the refused bitstream, and write the position
back. The server then reported `finished: true` for that film - written by the
native player, into the same table the browser player writes to.

**Two things the server had to change for the shell, and neither is a policy the
web page inherits.** The desktop shell is served from `http://tauri.localhost`
while its artwork comes from the local Theia process, so Chromium marks every
poster as a cross-site subresource: it refuses the `<img>` under ORB, and the LAN
boundary - which exists to stop a page on the network from reading this server
cross-site - refused it a second time. Both exceptions are opened to artwork and
to nothing else. `handleImage` sends `Access-Control-Allow-Origin: *` and
`Cross-Origin-Resource-Policy: cross-origin`; `nativeArtworkRequest` admits a
`GET` or `HEAD` under `/api/images/` **whose `Origin` is exactly
`http://tauri.localhost` or `tauri://localhost`** - a value a web page cannot
choose for itself - and the state-changing check further down is untouched, so
no write can ride it. `TestTauriArtworkCanCrossTheLANBrowserBoundary` asserts the
admitted request beside the refused ones: another path, another origin, another
method. Playback streams, the JSON API and the remote-access surface keep the
policy they had.

### Fourteen faults the runs found, and what they cost

None of these was visible by reading the code. They are the argument for running
the thing rather than reasoning about it.

1. **The resume point was refused.** `file-local-options/start` answers mpv with
   "error accessing property". A file-local option belongs to the `loadfile`
   command's own argument list, so the player now sends
   `loadfile <url> replace 0 "start=90.000"`. The stored position had been read
   correctly the whole time; only its delivery was wrong.
2. **The audio fallback sent the viewer back to the beginning.** Withdrawing the
   passthrough request reloads the film so it starts again on the PCM path - and
   that reload carried no resume point, so a film resumed at ninety minutes
   would have restarted at zero. The session now remembers where the film was
   asked to start and passes it to the reload. Measured: `pos 90.000` held
   through the fallback and advanced from there.
3. **The status the OSD reads was not JSON.** Flags were emitted by hand, so
   `pause` came out as mpv's own `no` instead of `false`. The OSD parses inside
   a `try`/`catch` and would have ignored every frame in silence: a blank
   player, no error in any log, and nothing to search for. The status is now
   built by the serialiser. Fifteen consecutive frames parse strictly; before
   the fix, none of them did.
4. **The phone control row painted a third of itself off the screen.** The
   player's furniture is drawn by a web page, and a web page at 390px is not a
   narrow desktop. Measured: 636px of content in a 390px window, with
   `button.control` boxes at left=365 right=417 and beyond - the row, not the
   library grid. Design system 6b forbids the row to wrap, so the fix is the
   control set, and the arithmetic is what decides it: six 3.25rem targets are
   312px of the 342px content box, so the row cannot hold a two-number clock
   beside them at all. Below 30rem the OSD therefore drops the volume, the
   language chip, the codec badge and the ten-second pair, and keeps play, the
   clock, the tracks popover, fullscreen and the way out - each still at its
   3.25rem floor, because 6b is explicit that whatever stays keeps it. 6b was
   amended in the same commit, since it is the authority on both surfaces.
5. **The hide rule lost a specificity tie.** Written as `.control--mute`, it
   did nothing: `button.control` is one element and one class and outranks one
   class whatever the source order, so the three controls stayed exactly where
   they were and the guard failed a second time at 395px. `button.control--mute`
   ties and wins on order. The same trap is documented in the web stylesheet for
   `.player-volume`, which is the argument for the guard rather than for
   reading.
6. **The library was drawn over the desktop.** The Tauri window is transparent
   and the OSD's page is transparent with it, which is right over a picture and
   wrong over nothing. Enumerated with no file loaded: the only children of the
   Tauri window were `TAURI_DRAG_RESIZE_BORDERS` and the WebView2 stack - mpv had
   created no surface at all, because `idle` and `keep-open` keep the engine
   alive between films without asking it to draw. `force-window=yes` gives the
   OSD a floor from startup; the same enumeration afterwards shows
   `class=mpv title="theia-player" visible=True`, last in the list, which is the
   bottom of the child z-order, exactly where the picture already goes. Nobody
   would have read this in the option list - every option was individually
   correct - and the consequence was a library floating over somebody's desktop
   icons.
7. **The panel showed part of the library.** `player_library` asked the server
   for sixty films and the OSD drew what it was given, so on the maintainer's 274
   -film collection most of it was unreachable from the player with nothing on
   screen saying so. A page is a sensible *first screen* and a broken *library*:
   the API is paginated, and the player now walks it. Measured against a bench of
   250 films: the whole library arrives in two requests - 250 films, 107 KB,
   0.7 s - where the fixed page returned 200, and 60 before that. `--limit` still
   asks for a page, and `--list` exercises the panel's own default rather than
   passing its own, which is how the first measurement came back 200 after the
   fix and exposed that the two paths had quietly diverged.
8. **A sidecar subtitle was invisible, and then the audio fallback took it away.**
   mpv finds a `.srt` beside a film when it is given a path, and cannot when it
   is given an HTTP URL: measured, the same film over HTTP reported four tracks
   and no selection where the local file reported five and chose the sidecar. The
   player now asks the server what sits beside the film and hands each text
   sidecar to mpv - which is also what makes the server notice a subtitle dropped
   into the folder that afternoon, since asking is what triggers its sidecar
   refresh. Two faults came out of building it, both found by running:
   `sub-add` issued straight after the audio fallback's reload answers "error
   running command" because mpv is still switching files, and *the first version
   added the sidecars once per load and never again*, so the film came back from
   the PCM fallback with its subtitles gone - the same shape as the resume point
   in fault 2, in the same function. The adds are now a queue retried on the next
   tick, bounded, and the reload refills it. Verified in one run: added, chosen
   (`sid=2`), refused by the endpoint, reloaded, refused once, added again,
   chosen again, and playing at 10.4 s with the subtitle on.
9. **A track was named after its URL.** mpv fills an empty `sub-add` title by
   deriving one from the address, and the menu read "6?profile=1". The player
   sends the language in the title position, and the OSD leads with the language
   whenever it has one - which is the web player's own rule
   (`web/src/lib/track-labels.js`), applied to a second surface. The guard now
   fails if any track name contains a URL, so the next person cannot reintroduce
   it by deleting one argument.
10. **Two guards would have kept passing after the rename.** Renaming an asset is
    the kind of change where the old name survives in the places nobody reads:
    `internal/updater`'s own string, its test expectations, the release workflow,
    the Makefile, the build script, two Playwright launchers, and the end-to-end
    verifier's second copy of the naming rule. Three of them were found by *the
    tests failing*, which is the good case - `TestAssetForRejectsAnUnverifiableRelease`
    builds its fixtures from old names, so after the rename it kept refusing them,
    for the wrong reason: the asset was missing as well as unverifiable, and a
    digest check that had stopped running would have looked healthy. Its fixtures
    now use `assetName()`, so the digest is the only thing under test. The other
    trap was silent in the opposite direction: `web/tests/serve.mjs` looks for the
    binary at the repository root, a stale pre-V3.3 `theia.exe` was still sitting
    there, and the browser guard would have run the old code and reported on it.
    Both launchers ask for `theia-server` now and name the stale file explicitly
    when they find it instead.
11. **The installer's confirmation threw its own answer away.** The last question
    of the form wrote into a `new(bool)` nobody read, so answering "Cancel"
    installed anyway - an installer whose only promise is that nothing happens
    until you agree, breaking exactly that promise. It was found by asserting on
    the confirmation rather than on the form: the answer is now part of the
    result, and `RunInteractive` returns `ErrCancelled` which prints "nothing was
    changed" and exits zero. Two smaller ones came out of the same test:
    `DescriptionFunc` is loaded through a command, so the summary of what is
    about to happen was *blank* in any test that did not run the form's commands -
    and for a player-only machine the summary said nothing at all, because it
    listed a data directory, a port and a library that machine will never have. It
    now leads with the declared role.

12. **The released installer could not find the released server.** `internal/setup`
    looked for `theia-server.exe`, which is what a working tree and `build.ps1`
    produce; the release publishes `theia-server-windows-amd64.exe`. Both are real
    names, nothing reconciled them, and the consequence was that an installation
    with **every published file in one folder** reported the server as missing and
    could not install its autostart entry - the one thing it does with that path.
    Found by putting the release assets in an empty directory and running the
    installer the way a person would, which is also when the fault above it
    appeared: with only the installer downloaded, the person gets a configuration
    for a product they do not have. Both are fixed: the installer accepts either
    name, beside itself and on `PATH`, and the release now also ships one archive
    containing everything (decision 121).

13. **An empty library broke the player's home screen.** The 3.3.1 server encoded
    a home screen with no rows as `"rows": null` - a Go nil slice - and the
    player decodes rows into a Vec, so serde answered `invalid type: null,
    expected a sequence` and the window said "the home screen could not be
    loaded", which is a sentence about a failure rather than about an empty
    shelf. Every previous run had films in the library, and the first
    installation with an empty one - what a fresh install has, and what the new
    `theia` command leads to - hit it immediately. Fixed on both sides, because
    two programs that update separately cannot assume they were built together:
    the server sends `[]` (`internal/library.HomeScreen`, guarded by
    `TestTheHomeScreenAlwaysAnswersWithARowListRatherThanNull`), and the player
    tolerates null from a server that is already published. Proven against the
    released 3.3.1 binary itself: the same window that said "could not be
    loaded" draws "This library holds no films yet" against it.

14. **The offline bundle shipped a server that was not the product.** The archive
    a person downloads (decision 121) is assembled in the player job, and that
    job built the server from the tree as it stands: no `embedded-web` artifact
    in `web-dist`, no `TMDB_API_KEY` in the environment. The binary it produced
    started, reported its version and scanned a library - everything the 3.3.0
    run measured - and then answered `/` with the **503 placeholder page**,
    "The server is running, the interface is not built", and logged
    `no TMDB API key configured, only cached metadata and artwork are
    available`. Measured after publication on the 3.3.3 and the 3.3.2 bundles:
    byte for byte the same size (17 496 064 against the published server's
    18 626 560) and the same two symptoms, so every archive released since the
    one-file download was introduced has carried it. The published
    `theia-server-<os>-<arch>` assets were never affected - they come from the
    build job, which downloads the artifact and receives the secret. Fixed in
    `release.yml`: the player job downloads the interface artifact, the assembly
    step is handed the metadata key, the archive's server is **run** and
    required to answer `/` with the interface and to report
    `TMDB metadata enabled`, and the published Windows server is scanned for the
    built application's `/_app/` asset path - 75 occurrences in a real build,
    none in the bundled one, which is how both checks were proved to
    discriminate before being trusted. The release was re-cut the same day
    rather than left to the updater: the first publication was withdrawn, the
    tag moved onto the fix, and run `35621749285` republished it - the archive
    now answers `/` with the interface and its own server logs
    `TMDB metadata enabled`.

The render harness is now `player/ui/scripts/render-check.mjs`, run by
`npm run check:render`, and it measures four phone states rather than one: the
library panel closed and connected, the control row playing, and the track
popover open. It was proven to fail before it was trusted - 507px, then 395px,
each naming the element that stuck out - and a fifth assertion counts the
visible controls, because a row that fits by dropping the play button would
otherwise pass. It also found that **the web player's own bar at a phone width is
guarded by nothing**: `web/tests/layout.spec.js` excludes the player on purpose
(it needs a real file to open) and `web/tests/playback.spec.js` never sets a
viewport, so it runs at 1280. By the arithmetic above the web bar - which keeps
the ten-second pair and the two-number clock - does not fit 375px either. That was
written down as a suspicion rather than as a measurement, and **22 September 2026
it was measured and turned out to be a fault with a different shape**: the bar fits
at 375px, and what breaks is narrower and depends on the film - with a three-hour
clock the row left the clock 53px of the 100px it needed at 320px, and 98px at
550px with the volume slider expanded. Below 44rem the web bar now drops the
ten-second pair, exactly as the native bar does at that width, and the playback
suite sweeps 320 to 768 with the three-hour clock rather than trusting one
fixture's 45 seconds. The verification record carries the row and section 6b the
rule.

### Run against a real library

Everything above had been measured against generated films and a synthetic bench.
The standard this project sets is the real collection, and that has now been run:
11 files, 118.2 GB, in a folder the maintainer actually owns, scanned into a
**throwaway data directory** so their own viewing history was never touched.

- **Scan**: 11 files found, 11 added, 0 removed, 0 merged, **0 problems**, in
  **1.03 s**. It resolved to 1 film and 1 series of 10 episodes; 2 items were
  enriched from TMDB, 0 were not found, 0 metadata errors.
- **The film** is a 53.79 GB Matroska remux, 8408 s. The server had never
  inspected it - its track list was empty, and the browser path would need a full
  remux (`reason=container_remux`). This is the file the whole pivot is about.
- **The bundled release player** - not a development build, the artifact
  `build-player.ps1 -Bundle` produces, run with no `THEIA_LIBMPV` - streamed it
  over HTTP and hardware-decoded it: `vo=gpu-next`, `hwdec=d3d11va`, duration
  8408 s, position advancing, zero configuration of any kind.
- **The tracks mpv found** in a file the server knew nothing about: HEVC video;
  **seven audio tracks** - TrueHD 7.1 **Atmos**, DTS-HD MA 7.1, and DD 5.1/2.0 in
  six languages; **six subtitle tracks** - two SubRip, one of them SDH, and four
  PGS bitmaps. A browser can pass none of those audio formats through and cannot
  render any of those bitmap subtitles.
- **The audio path held on real content**: the Atmos track was selected
  automatically, passthrough was requested, this machine's endpoint refused it,
  and the film continued on PCM **without restarting** - the fault from the
  fourth entry above, fixed and now observed on a real film rather than a
  generated one.
- **Resume**: the server's documented thirty-second floor means a 25-second test
  stores nothing, which is correct rather than broken. After a longer run it held
  47.5 s, and the next run opened at exactly 47.5 s and advanced from there. A
  film started in the browser is resumable in the player, on real files.
- **Nothing was written to the library**: the same 11 files, the same 118.2 GB,
  the same newest modification timestamp, **zero files modified** since the
  snapshot taken before the scan, and nothing new beside the films. A media
  server that writes into a media library is a media server people stop running.

**What this library also shows, and it is a real finding.** Ten of its eleven
items are episodes, and the player lists **one film**. The native player cannot
browse the maintainer's own series at all, so for this collection the pivot is
90% short of its purpose. It is a library-facing feature, so decision 97 applies:
it waits for a decision rather than arriving in this pass. It is the first thing
the next increment should carry.

### The library panel is the card grid

Offering films as a list of names would have been a second identity for the one
thing this product is, so the panel draws section 6 instead of approximating it:
a 16/9 backdrop at `w780`, `--radius-card`, a 1px hairline at rest and gold on
hover and focus, the title underneath in the UI face rather than the display
serif, and the one exemption 6.2 grants - a 3px gold rule across a part-watched
card, and only there.

Three things were decided rather than copied:

- **The panel's grid floor is `12rem`, not the `22rem` the text list used.** That
  figure was a reading measure for a line of text; a card is a picture, and 6.1's
  own floor is what a landscape still needs to stay identifiable. Below 36rem it
  is two fixed columns, exactly as 6.1 requires, and it is what puts four films on
  a phone screen instead of one.
- **The artwork URLs are resolved by the player, not by the OSD.** The interface
  never learns the server's address: `backdrop_url` and `poster_url` arrive
  absolute, and `image_url` trims both ends - a connection stores its base
  without a trailing slash and TMDB writes its paths with a leading one, which is
  how the test caught `http://host:8395//api/images/...` before it became a
  redirect per card.
- **The fallbacks are a state, not a browser decision.** Backdrop, then the
  poster *contained* rather than cropped to fill (a 2:3 image in a 16/9 frame
  loses its title off the top and bottom), then the title as text on a surface -
  never the platform's broken-image glyph, because a server whose image cache has
  not caught up is a normal state and not a fault. The state is *which URL
  failed*, not a boolean, so a card whose artwork arrives later draws again.

The harness asserts what a picture cannot: the number of cards, which of the
three fallbacks each one took, that every frame measures 16/9, that the progress
rule appears exactly once for the one part-watched film and not on the finished
one, and that exactly one film is offered as resumable. The 16/9 assertion was
proven to fail by making the frame 16/10 - "a card frame is 1.59:1, expected
1.78:1" - and the build was reverted to green.

### The metadata door, which nothing was watching (20 September 2026)

The maintainer reported that the card preview and the hero carried no synopsis.
Both were right, and neither was a rendering fault: `server.rs`'s `Metadata`
struct - the only door the server's metadata passes through on its way to the
OSD - carried `title`, `poster_path` and `backdrop_path`, and nothing else.
Measured with `--list`, which prints what the OSD is actually handed: the
metadata arrived with three fields where the API had sent twelve, so `overview`,
`runtime_minutes`, `vote_average`, `director` and `release_date` were dropped
one layer below the interface that draws them. `SeriesMetadata` was worse - it
carried no date field at all, so a series could not name its own year off the API.

The fix extends the three structs - movie, series, episode - to the fields the
interface consumes, and the series gains the air date, the tagline and the
overview. Verified in the running window over the real library: the series
preview draws `SHOGUN`, `Series · 2024` and three clamped lines of the French
synopsis the API sent, and `--list` now transports eight metadata fields where it
transported three.

**Why no guard caught it, which is the part worth keeping.** The harness mocks
`window.__TAURI__.core.invoke` and answers with its own fixtures, so the Rust
layer is never in its path: every assertion about the preview's synopsis passed
while the real player could not draw one. That is the same shape as the artwork
the harness used to answer by itself, and the lesson is the same - a harness that
answers its own questions proves the interface, not the wire. The wire is
`--list`, which is why the verification above is a command and not a sentence.

**The ladder is the server's, and it is real on this machine.** `/info` answers
six rungs for the film the request came from - the file itself, then 1440p, 1080p,
720p, 480p and 360p, `encoder=h264_amf`, `encoder_kind=hardware`. **A rung is the
converted route, and this was measured before anything was built on it**: `?h=1080`
on `/api/stream/{id}/files/{id}` returns the file itself - `206`,
`Content-Range: bytes 0-2000/57753069317`, `video/x-matroska` - because that route
serves bytes and ignores the height entirely, while `/remux?t=60&h=1080` answers
`200`, `video/mp4`, `Accept-Ranges: none`: a converted pipe. So a rung is a
different address rather than a property, and everything a pipe implies follows:
the film's clock is the `t=` it was asked for plus what the engine counts, seeking
is another request (mpv's `seek` on a pipe with no ranges cannot work), the length
comes from the server because a pipe has none, and **the sound is re-encoded at a
rung** - only the file's own rung reaches an amplifier untouched, which is why it
is the default and why no rung is remembered across films.

**The second fault was in the player, and the ladder exposed it.** A film paused
at any point left the *next* film paused too: mpv's `loadfile` keeps the pause
state, and nothing reset it, so a viewer who paused a film, went back to the
library and started another got a frozen picture with a play button that looked
like it was already playing. It is fixed where it belongs - a film started from
the library plays, whatever the engine was doing - and reloads keep the state the
viewer chose, which is both what they mean and what the engine already does.
Written down because the first attempt was wrong: `pause=yes` in `loadfile`'s
file-local options is ignored, and setting the property straight after the command
is lost when the new file starts. Measured, in the real window, on the real film:
a film paused before a quality change came back paused, one playing came back
playing, and one started from the library after a pause came back playing.

### What the shell connects to, and the flag that does not decide it

Measured on 20 September 2026, pointing the player at a server built from this
tree: `theia-player.exe --server http://127.0.0.1:8395` opened a window that was
talking to the machine's own installed server on 8383 instead. Nothing on screen
said so, and the two servers hold the same folder, so only the arithmetic gave it
away. The hero drew a resume state and *15 MIN LEFT* - and 8383 answered
`hero_kind: resume`, `position_seconds 7523.766` of `8408.032`, which is 14
minutes 44 seconds, while 8395 answered `hero_kind: featured`, position `0`.

The cause is the boot order in `App.tsx`: the shell asks the installed all-in-one
server first - `setup.json` says `all-in-one` and `config.json` says port 8383,
both under `%APPDATA%\Theia` - and returns as soon as it answers. A remembered
address and discovery are reached only when it does not. `--server` is a
Rust-side connection made before the window is shown, and the OSD then opens its
own; the flag's own comment says it exists "so the client can be exercised
without a click", which is exactly what it did not do.

Two things follow. The first is a consequence worth knowing before shipping the
pair; the second is a question rather than a defect.

1. **The artwork needs a server that carries the two header exceptions.** The
   same capture drew the NO SIGNAL card instead of the backdrop because 8383
   answers `/api/images/…` with no `Access-Control-Allow-Origin` and no
   `Cross-Origin-Resource-Policy` - read back with `curl`, not inferred - so the
   WebView refuses the picture under ORB and the documented fallback draws.
   Pointed at a server built from this tree, announced to the shell through a
   throwaway `THEIA_DATA_DIR` holding `{"role":"all-in-one"}` and
   `{"port":8395}`, the same window drew the real 59 048-byte backdrop. On a
   machine whose installation predates these commits, the shell therefore has no
   artwork until that server is refreshed: the two artifacts have to move
   together.

2. **Should an explicit `--server` win?** Today the machine's own installation
   outranks it, silently. That is defensible as the zero-configuration decision
   127 asks for, and indefensible as a diagnostic: somebody running two servers,
   or pointing the player at another household's, gets the one they did not ask
   for and no sentence saying which is connected. Changing it changes decision
   127 or the flag, so it is recorded here as a question rather than patched.

The server side of the same run, for the record: the real folder was scanned into
a throwaway data directory in **1.15 s** - 11 files found, 11 added, 0 problems,
resolving to 1 film and 1 series of 10 episodes, 2 items enriched from TMDB, 0 not
found - `--list` walked that film out of it, and the library itself was untouched:

| 200 columns | 76 | 76 | - |

Two things follow, and both are the intended behaviour rather than faults. The
form **stops growing at 76 columns**: past 100 columns the extra space is gutter,
which is what the cap was written for. And it **never exceeds the console**: at 80
columns it draws 71 characters in French and 74 in English, so nothing is clipped
at the width somebody is most likely to have. French is one line taller than
English, which is the accent count and the wordier sentences, not a layout
difference. Accented characters survived the round trip through the console at
every width - `é`, `è`, `ê` and `É` were all read back intact.

**Without colour, nothing is lost - measured rather than promised.** The plan asks
for the absence of colour to be checked "sans perte d'information", and it is the
kind of claim that is easy to write and hard to check. The console buffer was read
back twice from a real console, once with `NO_COLOR=1` in the launcher's own
environment and once without:

| | Colour | Text |
|---|---|---|
| `NO_COLOR=1` | one run, `fg=#CCCCCC`, **377 cells** | **478 characters** |
| without | three runs - `#CCCCCC` 249, `#C19C00` 77, `#767676` 51 = **377 cells** | **478 characters, identical** |

Two facts, and the second is the one that matters: the same 377 cells are painted
either way, so nothing is dropped or added, and the 478 characters read back are
**identical**. What `NO_COLOR` removes is the division between the three
registers - the wordmark and the selected option stop being gold, the hint stops
being grey - and every question, option and hint survives as text. `--check` draws
no colour at all through a pipe, which is why it is not the instrument here: the
theme's colour only exists on a real console.

**What the photographs of this cannot show, and now say so.** `capture-tui.ps1`
framed the console by asking the console host for its window, which is correct for
a classic conhost and **wrong under Windows Terminal**: there the console host
owns a pseudo-console, moving it moves nothing on screen, and the capture is of a
rectangle the interface was never in. That produced a picture whose right-hand text
was cut off - reported during this campaign as a clipped installer, and it was not
one. The script now takes `-FrameTitle` to frame the window the terminal actually
shows, and warns rather than guessing when no such window is found; on this machine
the visible frame is a Windows Terminal tab, which no title of the program's own
choosing reaches. The cell measurements above are unaffected, because they read
the buffer instead of photographing it. **A framed screenshot of the installer at
80x24 and 100x30 remains unverified here**, and the 120x40 pair in `phase5/` is a
full-screen capture rather than a window crop.

**Leaving without installing, run against a disk rather than a struct.** The
escape path had been tested since the form was written, and what it asserted was
that a field named `aborted` becomes true. The sentence somebody is shown is
`cancelled`, and its entire content is that nothing was written - so that
sentence is a promise about a filesystem, and it was checked like one. Five
guards in `internal/setup/cancel_test.go` now call `RunInteractive`, the entry
point `main` calls, with a redirected `APPDATA` and temporary data and
installation directories, and then walk all three:

- Control-C and escape are still *bound* (`keyMap().Quit.Keys()`), because the
  label under the question is worth printing only if the key does something.
- An aborted form writes nothing - and the reason this needed its own guard is
  that `Confirmed` starts at true, deliberately, so the `aborted` flag is the
  only thing between an escape on the first page and an installation nobody
  asked for.
- Escape sent as the byte a terminal sends, through `RunInteractive`, returns
  `ErrCancelled` and writes nothing.
- The data directory and the installation directory are not merely empty: they
  do not exist. An empty directory is still something somebody has to explain
  to themselves a year later.
- Nothing at all appears under `APPDATA`, which is where the Start Menu folder,
  the Desktop shortcut, the logon entry and the applications-list registration
  live - the four things a person would otherwise remove by hand.

**The flags, driven through the binary rather than the functions.**
`--from`, `--force` and `--uninstall` are not functions, they are wiring: a flag
parsed in `main`, handed to a helper, and turned into a `Source` or a call. A test
of `Source{Force: true}` cannot see a flag that reaches nothing, and `--force` is
a flag that once reached nothing. `cmd/theia-setup/flags_windows_test.go` builds
the real `theia-setup.exe` and runs it as a subprocess with a redirected
`APPDATA`, `LOCALAPPDATA` and `USERPROFILE`: `--service` without `--yes` is
refused *before* it writes (autostart entries are a change to somebody's machine,
and the refusal is checked to have created neither directory), `--uninstall` on a
machine with nothing installed exits 0 and leaves the watch history alone, and
`--check` in three shapes writes nothing at all.

**Unverified, and the reason is structural.** A full `--from` install driven
through `main` was **not** run. The installation registers itself under
`HKCU\Software\Theia`; the registry has no `APPDATA` to redirect, and the key name
is a constant in a non-test binary, so the suite's own `TestMain` redirection -
which covers the in-process tests - cannot be inherited by a subprocess. Running
that path here would have written the maintainer's real applications-list entry.
It is the one flag path left to a machine where that entry is expendable, and the
library-level tests (`TestAReleaseFolderBesideTheInstallerIsInstalledWhole`,
`TestAReleaseArchiveIsInstalledWithoutUnpackingItFirst`) cover the same work one
layer down, with `--force` and `--from` reaching `Source` in `runOnce` read by
eye rather than by execution.

**Not verified.** The install was not tried against the real GitHub release page,
because V3.3 is not published yet - the stub serves the same bytes with the same
digests, which is every part of the path except the API's own availability. A
double-click on an entry was not exercised either, though the player itself was
launched from the path the entries name.

### Launching it, which is what the launcher question was really about

The paragraph above was written before the launchers were driven, and one line of
it - "no launcher was driven" - is now out of date. What follows is what was
measured, on the maintainer's machine (Windows 11, 200% display scaling).

**The applications list.** After a real installation, the registry entry was read
back with PowerShell: name, version `3.3.0`, publisher, install location, icon,
`EstimatedSize` 134738 KB, install date, and
`"C:\...\Programs\Theia\theia-setup.exe" --uninstall` - a command whose target
exists. Enumerating both uninstall roots, which is what the Settings page walks,
lists **Theia 3.3.0**. `theia-setup --check` reports `Application : oui`.

**Windows' own search.** The Windows key, then "theia": *Theia Player* as the best
match, *Theia Server* under Applications, both carrying the product's icon rather
than the generic executable glyph. This is the check the maintainer asked for in
their own words - "quand je recherche... il n'y a pas de TA Server" - answered by
the shell itself.

**Flow Launcher.** Its Program plugin has `EnableStartMenuSource` and
`EnableRegistrySource` both true, which is where both of the installer's records
live. Its process was restarted, its own hotkey (Alt+Space) was pressed, and
"theia" was typed: the results list **Theia Server** and **Theia Player**. Its
`LastIndexTime` in the plugin settings still read 14:52 after that, so the field
is not the index that answers a query - recorded because it was the reason to
expect the entries to be invisible, and they were not.

**The player, launched.** Started from the installed copy, it opened a window
titled *Theia* and drew its connect screen: the library panel, the address field,
the gold connect button, and "Aucun serveur détecté sur le réseau" - the right
state with no server running.

**Uninstall, run for real.** From the installed copy, `--uninstall` reported the
four shortcuts and the registry entry removed, the data directory untouched, and
the folder "removed as soon as this program closes". Three seconds later: the
Start Menu folder and the desktop entry gone, the key gone, `%LOCALAPPDATA%\
Programs\Theia` gone, the six entries of `%APPDATA%\Theia` still there, and no
removal script left in the temporary folder.

That last sentence is the second version of the mechanism. The first used
`MOVEFILE_DELAY_UNTIL_REBOOT`, which needs administrator rights this installer
never asks for, and the real uninstall answered "some files could not be removed"
about a folder holding nothing but the tool that was running from it. The
replacement - a randomly named command file that waits for the asking process to
exit - took three failed shapes to get right, all of them failing silently with
exit status 0 because Go quotes arguments the way a C runtime expects and cmd.exe
does not read backslash escapes. The working shape is pinned by a test that drives
it against a folder whose path contains a space.

**A fault that turn found, and one that was not one.**

- **The control row overflowed between 480 and 684 pixels.** Measured by the OSD's
  own render check at 550px: 636px of content in a 550px window, and a horizontal
  scrollbar in the installed player on this machine, because 200% scaling turns an
  1100-pixel window into 550 CSS pixels. The rule that drops controls was written
  for 30rem (480px), and the harness had only ever drawn 390 and 1280. The drops
  now happen at 44rem; the language chip stays until 30rem, because the native
  player has nowhere else to switch it. Design system §6b carries the measurement.
- **A false alarm worth recording, because it cost an hour.** A capture taken from
  a DPI-unaware PowerShell asked for a 1100-pixel window and got one 2200 pixels
  wide, so the picture was clipped by the *screen edge* while the OSD had laid
  itself out correctly all along. The render check disagreed with the photograph
  and was right. `scripts/capture-window.ps1` now declares per-monitor awareness
  before touching a window API, and prints the DPI it found.
- **A probe that paused the thing it was measuring.** "Movement at two instants"
  was first answered by a script that took the foreground with a real click,
  because `SetForegroundWindow` is refused when another process owns it - and in
  this product **a click on the picture is a playback command**. The film paused,
  the Space meant to resume it did not reach the WebView2 focus, and the two
  captures came back byte-identical. The report was "nothing moved", while the
  engine was playing perfectly. What settled it was the fixture painting its own
  timecode and frame number: both captures read `00:00:00.825`, frame 21 - eight
  seconds apart, the same frame. Taking the foreground by `AttachThreadInput`
  instead of by clicking removed the interference, and the same probe then read
  frame 21 and frame 211. **A guard that changes the state it measures is not a
  guard**, and this is the third shape that lesson has taken in this project.
- **A GUI binary has no stderr to redirect.** `Start-Process -RedirectStandardError`
  on `theia-player.exe` produced a zero-byte file while the player was demonstrably
  playing: the process has no valid stderr handle in that arrangement, and writes
  to it go nowhere. The engine's own diagnostics are still readable through the
  headless path (`cmd /c "theia-player.exe --media <file> --diagnostics"`), which
  is how the 60-second measurement and the phase 4.3 reading were taken. A
  diagnostic that silently produces nothing is worth a line here, because it looks
  exactly like a program that says nothing.

## Open risks

1. **Composition is decided, with one confirmation outstanding.** Spike A2b
   chose `wid`: mpv draws into a child window of the Tauri window, and the
   WebView2 stack is already above it without help. What no program can settle
   from here is whether the *pixels* composite correctly - whether a film is
   visible through the transparent OSD. That check belongs to the maintainer,
   and it is the only result that could overturn the choice in favour of
   `mpv_render_context`.

2. **The libmpv artifact is not durable upstream - resolved by decision 118.**
   The player bundles a pinned LGPL build instead of downloading it, because
   upstream keeps thirty days of builds. The residual risk is therefore a
   licensing one rather than an availability one: the build's author states he
   cannot guarantee that every LGPL-incompatible package was disabled, and the
   maintainer accepted that knowingly.
3. **No amplifier on the validation machine.** The whole point of the pivot -
   TrueHD/Atmos and DTS-HD MA reaching a receiver untouched - cannot be proven
   here. Spike A3 proves the request path and the refusal path; the acceptance
   path needs a machine with an HDMI audio output and an AVR.
4. **Two FFmpeg builds on one machine - resolved by decision 142.** libmpv
   carries its own; `theia-server` downloads another for conversion. The question
   was whether the player can reuse the server's, and decision 142 answers it
   with the measurements: FFmpeg is compiled *into* `libmpv-2.dll` (its PE
   import directory names 47 DLLs and every one is a Windows system library - no
   `avcodec-*`, no `avformat-*`), the server's runtime is an executable pinned to
   a `-gpl` build and read as `--enable-gpl --enable-version3`, and the two stay
   two because merging them is an engine rebuild against shared FFmpeg, against
   the LGPL commitment `player/NOTICE.md` makes in writing, and for a saving of
   183 MiB on a machine that has both.
5. **The pivot has no field evidence.** Decision 97 asked ten households for
   data and received none. This generation is argued from platform limits, and
   the record says so rather than implying a demand that was never measured.
6. **The native window at its declared minimum - closed on 22 September 2026,
   and the units on record were wrong.** Decision 124 and the table above both
   said `minWidth: 640` is 320x180 CSS at this machine's 200% scaling. The window
   itself answers `WM_GETMINMAXINFO` with `ptMinTrackSize` **1280x720 real
   pixels**, so the value is in *logical* pixels and the declared minimum is
   **640x360 CSS**; 320x180 CSS is a size *below* it, reachable by a program
   asking - the earlier campaign's external `MoveWindow`, and this run's Tauri
   `set_size` - and not by dragging an edge.

   Both sizes were then photographed from inside the application, with a film
   playing. At 640x360 real the OSD has exactly 320x180 CSS (`innerWidth` 320,
   `devicePixelRatio` 2) and **draws its bar**: 320 wide, 128 tall, pinned to the
   bottom, three visible controls and a clock reading only its elapsed time -
   decision 124's rule seen in a real WebView2 window rather than in the render
   check. At 1280x720 real, the floor a viewer can drag to, four controls are
   visible and the clock draws `0:08 | 0:20` with its hairline. The earlier
   picture of the smaller size with no control bar at all was the probe, not the
   product: the OSD fades its furniture after three seconds, foregrounding a
   window is not input the page sees, and the bar was in the DOM throughout
   (`hidden: false`, `display: flex`, 320x128) - the run with a keystroke and the
   run without it differ in exactly that field. Pictures, the numbers the player
   wrote itself and a `--diagnostics` run are in `docs/archive/v3.3-min-window/`;
   decision 124 carries the correction.

7. **The old pointer-hide risk is closed by changing the product rule.** The
   WebView2-owned cursor could not be hidden reliably from either CSS or the
   Tauri process; it flashed every few seconds. The native shell now leaves it
   stably visible while only the furniture fades. In the installed rebuilt
   player, after four idle seconds with the pointer over the window,
   `GetCursorInfo` reported it visible in **48 of 48** samples. The product no
   longer asks the platform to do the thing it repeatedly proved it could not
   hold.

8. **The pointer cannot be parked from a script on this machine, so a native
   photograph of a hover state is not reachable here.** Measured on 20 September
   2026 while trying to photograph the caption bar's hover plate: a DPI-aware
   `SetCursorPos(2101, 92)` reports back `2101, 0` - x is honoured, y is not - and
   with no player, no probe and nothing of ours running at all, `GetCursorPos`
   still reads `1051, 0`. So the reading is not the shell's doing, and it is not
   DPI virtualisation either, which is what the first attempt looked like: the
   process declared per-monitor awareness before touching anything, and the screen
   then reported its real `2880x1800`. A hover state is therefore verified by
   measurement and by Chromium's own painting - `assertCaptionChrome` reads the
   plate's computed colour and alpha, the chip in both states, the box against the
   cell and the pitch, the flush close cell and both edges, and writes
   `render-check/9-caption-hover.png` - and not by a photograph of the real window
   under a real pointer. **A screen capture is not the only way back either**: the
   window's rounded region is read directly with `GetWindowRgn` and `PtInRegion`,
   which settled the corner question without a picture at all. What still wants
   the maintainer's eye is the look of the whole thing, not a CSS rule.

9. **The macOS player draws the film itself, and only a runner has shown it.**
   Decision 144: with the pinned engine there is no window-presenting video output
   on macOS at all - `vulkan`, `macos-cocoa-cb` and `swift-build` are disabled in
   its build, and the dylib's load commands name no AppKit, Metal, QuartzCore or
   Vulkan - and mpv 0.41 removed `--wid` with the file that read it. So Theia owns
   a GL context and calls `mpv_render_context_render` for every frame, with the OSD
   composited above it in the same window. That is the path the Windows player
   refused on purpose (spike A2b chose `wid` to avoid owning a device and a
   swapchain), and it is now the only one.

   **Two throwaway spikes are the gate, and both need the Mac**:
   `player/spike-macos/render-spike.m` (does `mpv_render_context_create` succeed
   with this pin, and do frames arrive in an `NSOpenGLView` we own?) and
   `player/spike-macos/composite-spike.m` (does a transparent `WKWebView` composite
   above an `NSOpenGLView`, and does the page still receive clicks through its own
   transparent areas?). Each prints what it observed and says what to look at.

   If the first fails, **the pin is wrong for macOS** and a self-built engine
   becomes the answer - mpv + FFmpeg + libplacebo with Vulkan, or with
   `cocoa-cb` - with its own source pin, digest and licence check, which is a
   decision rather than a repair.

   **The gate that paragraph set was met on a `macos-14` runner, the substitute
   decision 144 named** - real Apple Silicon, since this project has no Mac - and
   both halves of it are a photograph: `mpv_render_context_create` succeeded with
   `MPV_RENDER_API_TYPE_OPENGL`, frames arrived in the host's own `NSOpenGLView`
   and the film appeared in the window the player owns; and a transparent page's
   control bar was photographed **over** that GL surface in the same window. The
   real player then played a film on that machine (`ao=coreaudio`, the audio mode
   honestly `pcm`) and `scripts/verify-macos.sh` read back `21 passed, 0 failed,
   2 for a person to look at` on 23 September 2026. So the pin holds and no
   self-built engine is needed. **V3.3.4 published the four macOS names on 23
   September 2026** - run `35821865718`, fourteen assets, `theia-setup-darwin-arm64`,
   `theia-3.3.4-darwin-arm64.zip`, `theia-player-darwin-arm64.zip` and
   `theia-launcher-darwin-arm64` - and the row above carries the measurements.

   **What the runner could not answer stays open, and needs a Mac with a person
   at it**: the virtualised machine accepted `hwdec=videotoolbox` and then refused
   it (`Failed setup for format videotoolbox_vld`), so hardware decoding still
   needs one, and so do a real audio endpoint, Gatekeeper's first refusal of an
   unsigned download, and the question no program settles - whether the OSD reads
   well over a moving film.
